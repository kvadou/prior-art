# Annotated reference board

Use the smallest useful format: a Markdown contact sheet, local HTML board, design
file, or annotated screen sequence. No particular design tool is required. A list of
image links without decisions is not a completed board. With no image access, use
explicitly labeled textual observations and state the visual evidence gap.

For each selected reference retain:

| Field | Content |
| --- | --- |
| Source | Product, exact source URL, retrieval date, version/plan when known |
| Evidence | Interacted / observed demo / static reference / inferred |
| Job and state | What the person is trying to do; where this screen sits in the flow |
| Artifact | Local screenshot/design artifact or permitted public reference; viewport if known |
| Pattern | Specific hierarchy, interaction or relationship worth considering |
| Mechanism and fit | Why it may help this user's job; evidence versus inference |
| Adapt / reject | What transfers, what conflicts with our brand, density or constraints |
| Check | Concrete scenario that would validate the proposed use |

Group by decision or task, such as record context, pipeline scanning or follow-up
capture, so alternatives can be compared. Preserve enough surrounding screen context
to understand navigation. Capture only what is needed; avoid unrelated private data.
Follow the privacy/storage rules in [product-experience](product-experience.md).

A useful annotation: "This profile keeps record identity visible while the activity
panel changes. Adapt the stable identity area; test switching between notes and work
without losing the selected company." This is a design hypothesis, not proof of a
measured productivity gain.

Keep source artifacts distinguishable from generated wireframes. A synthesized
mockup is our proposal and must never masquerade as an observed competitor screen.
